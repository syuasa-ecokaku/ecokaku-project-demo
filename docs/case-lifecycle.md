# 新規案件起案・変更登録（公開モック）

## 実装場所

`index.html` 内の iframe の実コードを拡張。共通UI・案件カタログ・既存の部門別保存／承認アダプターを利用する。独立した第二の承認フローは作らない。

- 不動産開発／電力申請の見出し右上：新規案件起案。選択事業を初期設定。
- 全7部門の案件詳細上部：変更登録、共通情報、変更履歴。
- 各履歴の選択：変更前／変更後の保存時点の情報を読み取り専用で表示。
- 太陽光／データセンターの電力申請：起案案件の共通情報・既存の正式化条件の確定日だけを表示。未定義の業務工程を蓄電池からコピーしない。

## ID・採番

既存案件の内部キーを維持。新規案件は `case-<UUID>` を不変の内部ID／部門データのキーとする。`baseNumber` と `formalNumber` は表示番号であり外部キーではない。事業は番号から推測せず `businessId` で管理する。

R/G/P各系列の既存番号・旧番号・変更履歴・予約済みP番号の最大値から次の5桁番号を決める。キャンセルやエラーで番号を消費しない。既存案件候補を開く場合、同じオブジェクトに必要な部門参照を追加し、別番号／別案件を作らない。同一所在地は候補確認後に別案件として登録できる。

変更登録は案件共通の `revision` を増やし、保存成功時だけ `基本番号-01` 形式にする。通常保存では枝番を増やさない。変更登録には未保存の下書きを先に保存／取消する必要がある。過去番号は検索対象として保持する。

正式化は従来どおり、保存済みの `powerConfirmedAt` と不動産の取得済ステータス＋取得完了日を確認し、既存の管理者／承認者が実行する。正式化自体では枝番を増やさず、P番号を新しい枝番なしの基準とする。内部ID・旧番号・仮番号時代の変更履歴・契約IDは維持する。

## データと保存

従来は画面内保存のみだったが、今回の再読み込み復元要件に合わせ、案件・部門情報・承認・ファイル名・変更履歴を一つのスナップショットでブラウザー内に保存する。入力途中の下書き、通知既読、ユーザー切替、設定は永続化しない。

iframe の `sandbox="allow-scripts"` は維持する。opaque origin の iframe 自身から localStorage を開かず、親ページの限定されたメッセージハンドラーに保存を委譲する。送信元ウィンドウ、読み込みごとのトークン、メッセージ種別、保存スキーマを照合する。任意キーの読み書きAPIは公開しない。

保存キーは `ecokaku-project-demo:case-lifecycle:v1:<ページパス>`。`index.html` と末尾 `/` の違いは正規化する。保存先は現在のブラウザー・オリジン・パスに限定され、端末間／部門利用者間のサーバー共有ではない。

案件更新・番号・履歴・承認状態を一回の localStorage 書き込みで確定する。保存成功の応答後に成功表示する。容量不足・アクセス拒否・古いタブの競合は案件／枝番／履歴／下書き・通知状態を戻す。応答を確認できない場合は成功と表示せず、再読み込みを案内して次の保存を止める。

同じオリジンの別タブとは連番シーケンスを比較し、対応ブラウザーでは Web Locks により保存判定と書き込みを直列化する。非対応ブラウザーの同時書き込み、複数端末・複数利用者による採番の一意性は保証しない。本番ではサーバーのトランザクション、一意制約、認証・認可が必要。

関連資料は既存どおりファイル名だけ。本体のアップロード、永続保存、ダウンロードは未実装。削除されたブラウザーデータや別オリジンには復元できない。容量にはブラウザーの上限がある。読み込み失敗時は既存保存データを上書きせず、エラーを表示して保存を止める。

## 検証

`python tests/case_lifecycle_smoke.py`：Chromiumを使うブラウザーテスト。R/G採番、必須エラー・キャンセル・連打、7部門参照、候補から既存案件を開く、連続枝番、通常保存、読み取り専用履歴、既存承認との接続、P番号後の枝番リセット、容量不足の巻き戻し、再読み込み復元、太陽光／データセンター、複数タブの競合、PC／スマホのモーダルを確認する。

既存の承認テストは、再読み込み時の期待値を今回の永続化要件に合わせて更新する。既存の業務データ・案件番号・工程番号は変更しない。
