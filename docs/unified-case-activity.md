# 案件全体の稼働・終了判定の統一（④）

## 対象・既存実装

`index.html` の既存iframe内を変更する。作業開始点は `23a4e0d`、mainは `5192e9a`。①保守契約・②個別作業の改修を含むブランチから継続する。AGENTS.mdは環境内で見つからず、既存の未追跡 `.agents/` は変更しない。

③という独立した追加実装・ブランチは現環境に存在しなかった。既存の `maintenanceOnly`／受託ルート、正式化承認情報を使用する案件分類を維持し、全社KPIに仮案件R/G・正式案件P・保守単独Mの内訳を表示する。表示番号の先頭文字や枝番を稼働判定のキーにしない。

①の契約編集・締結・終了・更新、②の記録IDを保つ実績登録・完了・中止・理由付き訂正、P引継ぎ・M単独受託、正式化承認、枝番発行、保存先は維持する。

## 状態の役割と共通判定

案件全体は既存の `source.projectStatus` を正本とする。互換参照として旧 `lifecycleStatus` を読む。部門の `status`、工程の `phase`、メンテナンスの `caseState`、個別契約・点検対応の状態を案件全体の終了へ変換しない。

| 対象 | 全社の稼働対象 |
| --- | --- |
| R/G、保守引継ぎ前／受入済みP | 案件全体が継続中 |
| 保守単独M | 案件全体が継続中、かつ受入済みでメンテナンスが管理中 |
| 案件全体が終了／中止／廃止 | 対象外 |

`caseWholeState`／`caseBusinessActive` を全社KPI・連動一覧・進捗グラフに使う。`caseMaintenanceManaging` は同じ全体状態とメンテナンス状態から管理中案件・管理設備を集計する。稼働は発電設備の運転状態ではなく、業務上の継続管理と画面に明示する。

未設定・未知の旧全体状態は確認対象と表示し、確認までは暫定継続として扱う。無言で終了せず、過去の終了日・理由・実行者を作らない。新規起案には継続中を明示して保存する。旧全体状態の「完了／完了済み」は終了の互換表記として読むが、部門や工程の同表記は使わない。

## 操作の設置場所

- 共通案件情報：案件全体の状態、全社稼働対象、終了日・理由、残務、履歴、「案件全体を終了」「案件を再開」。全7部門の既存共通詳細から使う。トップ専用の旧案件詳細にも同じ操作を置く。
- 保守受入済み案件の共通情報：「メンテナンス終了」「メンテナンスを再開」。通常の案件状態欄から終了を選んだ場合も同じ確認フォームを開く。
- 継続残務がある共通情報：「残務完了を登録」。案件全体を終了する前に、残務を明示的に解消する。
- 既存の案件検索：案件全体の状態フィルター（継続中／終了／中止／廃止／すべて）。部門進捗・保守状態とは別条件。通常は継続中、共通解除でも初期値へ戻す。
- 全社トップ：「案件全体の状態で検索・過去案件の確認」。全社稼働KPIとは独立した過去案件の検索導線で、同じ案件・部門詳細を開く。

## 終了前の確認・禁止条件

終了日は当日以前の実在日、理由は必須。保守契約、未完了／状態未確認の点検・対応、他部門の未完了業務を保存済みデータから表示し、該当案件の画面へ移動できる。

- 締結済み保守契約の実効終了日（元の終了日と登録済み終了日の早い日）が終了日より後、または期間未確認なら終了を止める。未来開始の締結済み更新契約も含める。終了日同士が同日なら許可する。契約自体は当日まで有効という①の境界は変えない。
- 未完了・状態未確認の個別作業があれば、専用フォームでの解消・確認を案内する。終了操作で作業や契約を自動更新しない。
- 作業実績、工事実績、受電送電実績、契約締結、管理開始・受入・既存保守終了が指定終了日より後なら矛盾として止める。
- 案件全体の終了には、受託・管理中のメンテナンスや、対象部門の明示的な進行中業務が残らないことを要求する。未保存の下書きも先に保存または取消を案内する。

部門の対象判定は `casePendingStatuses` の明示的な既存状態、申請済みで受電送電未実績の電力工程、未完了の電力タスク、契約の確認・承認状態を使用する。未着手・未着工・調査前・対象工程前・対象外は状態だけでは未完了にしない。期限や自由記述があるだけでも未完了にしない。今後ステータスを追加する場合は対象判定にも明示的な定義が必要。

## 残務・再開

メンテナンス終了では、案件全体も終了するか、他業務のため継続するかを選ぶ。継続には理由・部門・次の対応が必須で、`continuation` として同じ案件へ保持する。継続担当者はその部門の既存担当者を参照する。Pは全社稼働に残り、主担当・次の対応を継続担当へ切り替える。Mは全体継続でも保守終了後は全社稼働に入れず、残務を部門別要対応へ表示する。

部門別要対応は残務を含む業務件数であり、全社稼働中件数とは別の意味と説明する。残務完了の明示操作後も、他の未完了業務があれば案件全体終了を止める。

案件全体の再開は理由必須。同じID・番号を保ち、保守や契約を再開しない。保守の再受託・再開も理由と状態を指定する専用操作とし、過去の終了履歴を保持する。終了後の新規契約・締結・更新・作業／設備追加は再開を案内する。完了作業の理由付き訂正は可能で、訂正だけでは再開しない。①の終了済み契約の参照専用ルールは維持する。

## 集計・保存

- 全社の稼働KPI、R/G・P・M内訳、一覧、進捗グラフは共通の稼働対象から算出する。
- 保守終了／案件全体終了は管理中案件・管理設備に含めず、通常の今後予定も除外する。過去の資料・作業・契約は残す。
- 請求残額は稼働対象で絞らず、発行済み売上請求の全案件を参照する。終了しても未入金額を除去しない。
- `projectStateHistory` に内部案件ID、操作、日時、利用者、理由、状態と残務の変更前後を保存する。枝番の `changeHistory` とは区別する。保守終了の要約は既存の保守イベントにも記録する。
- 既存の `lifecycleTransaction` で状態と履歴を一体保存。失敗時はまとめて復元し、入力フォームを保持する。連打・古いフォームからの確定を防ぐ。取消では既存下書きを消さない。
- 同じブラウザー内の既存保存方式を継承し、再読込で復元する。別台帳・新しい保存キー・外部接続は追加しない。

## 残る制約

本番の認証・権限強制、サーバー共有、複数端末の更新保証は既存モック同様に未実装。ファイル本体は保存せずファイル名のみ。状態変更は既存の担当者が操作するデモで、新しい承認フローは追加していない。新しいステータス・部門固有の残務判定は、業務定義が増えた際に対象定義の追加が必要。未知・未設定の旧案件全体状態は人による確認対象として表示する。

本ブランチではmainへのマージ・本番公開は行わない。
