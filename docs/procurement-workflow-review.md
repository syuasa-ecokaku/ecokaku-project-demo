## 変更画面と保存

購買に「サマリー／発注管理／入出庫・在庫／移管管理／請求・支払予定」の5タブ。既存の色・表・事業切替・案件参照・通知を利用。サマリーカードで未納／納期超過／引当残／当月予定へ移動し、現在の絞り込みを引き継ぐ。

発注詳細の①〜⑤・随時の入力区分による段階入力（追加仕様は[入力区分レビューガイド](procurement-input-sections-review.md)を参照）。明細の追加・修正、分納・役務完了、未納残取消、倉庫と直送、使用予定と確定引当、引当解除・一部出庫、移管申請・詳細・確認・完了・取消、請求の確認と資料名、複数の支払予定・請求紐づけ・差額を操作できる。

保存先は既存キー `ecokaku-project-demo:case-lifecycle:v1:<URLパス>` のsnapshot内 `procurement`。親ページが書込みを確定し、同一URL・同一ブラウザーなら再読込後に復元。別端末・別URL・別ブラウザーとは共有しない。保存失敗時はデータをロールバックし、フォームを残す。既存の更新シーケンス照合・排他処理を利用する。添付はファイル名のみ保存。本体の送信・保管・プレビューは行わず、その旨を画面に明示。

「レビュー用データを初期化」は確認画面を経由し、購買台帳だけを復元。他部門や案件カタログの保存内容は保持する。

## データ構造

すべての5タブが次の共通台帳を参照する。実績にExcel行番号・名称・所在地を外部キーとして使わない。

| 管理単位 | snapshot内の配列 | 主な関連 |
| --- | --- | --- |
| 発注 | orders | id、business、supplier、purpose、term |
| 発注明細 | lines | id、orderId、caseId、productId、cancelled |
| 納品／入庫実績 | receipts | id、lineId、route、location、qty、unusable |
| 在庫引当 | allocations | id、caseId、business、productId、location、qty（残） |
| 出庫実績 | issues | id、allocationId、caseId、productId、location |
| 移管 | transfers | id、business、fromCase/toCase、fromLocation/toLocation、status |
| 仕入請求 | invoices | id、orderId、lineIds、独立した請求日/受領日/確認日 |
| 支払予定 | payments | id、orderId、invoiceId（任意）、autoSlot（自動予定の同一性） |
| 使用予定 | usagePlans | id、caseId、productId、location。確定引当とは別 |
| 旧番号の対応 | caseAliases | caseId、legacyNumbers。案件の内部IDが関連付けの基準 |
| 操作記録 | events | id、date、text |

案件向け・引当・移管は既存の `source.internalId` を使用し、事業の不一致を拒否する。在庫向けで未定の案件には空値を使用し、P番号を生成しない。製品マスターIDは名称・型番・基準単位を固定し、在庫を事業×製品×場所で計算する。

在庫は入庫実績−出庫実績±完了移管で算出。未納発注・費用・直送を加算しない。利用可能は実在庫−使用不可−引当残。出庫は引当残と実在庫を同時更新。移管完了は状態を検証して一度だけ反映し、必要な引当を先の案件・場所へ付替える。全社在庫を増やさず、支払予定を追加しない。

## サンプルと操作手順

既存案件がある事業に `DEMO-BATTERY-001/002`、`DEMO-SOLAR-001/002` を用意。案件が未登録のデータセンターは空状態を保ち、在庫向け発注は新規登録できる。

1. 購買→蓄電池→発注管理→`DEMO-BATTERY-001`の詳細。パネル12枚、PCS2台、送料1式。パネル4枚が納品済。「入庫を登録」で数枚を分納し、納品済数と未納数の更新を確認。PCSは「直送納品を登録」。送料の「役務完了」は在庫を増やさない。
2. `DEMO-BATTERY-002`は案件未指定の在庫購入。杭30本中20本、通信装置4台を架空第一倉庫へ入庫済。杭2本は使用不可、10本を引当→4本を出庫した結果、杭の実在庫16本・引当残6本・利用可能8本・未入庫残10本。追加で引当・出庫・解除を操作。
3. 移管管理→杭2本の案件間移管を「確認済にする」→「移管を完了」。同一倉庫の実在庫を保ち、案件の引当先だけを変更。通信装置1台の倉庫間移管を完了し、第一倉庫3台／第二倉庫1台を確認。完了後に再完了ボタンが出ないことを確認。
4. 請求・支払予定→001は50/50、002は30/70。発注金額と予定合計を比較。条件から再作成しても自動予定の件数・IDは維持される。既存予定に請求を紐づけても予定額は増えない。002の残金は2026-12-31。未確定日・未確定額の予定を追加し表示を確認。
5. 新規発注→案件向け→基本情報を保存→明細追加。製品を複数追加し送料を費用として追加。税込計算を確認。未納残取消は納品済実績を保持する。予定と請求との差額は残すため、担当者が見直す。
6. 再読込で復元を確認し、「レビュー用データを初期化」で戻す。

## 仮設定と購買への確認事項

- 数量は整数、単価は税抜の整数円、税額は明細ごと切捨て。10％・軽減8％・非課税/対象外を代表値として選択。端数規則、税区分の適用、外貨や小数数量の必要性は要確認。
- 自動予定の対象金額は未納取消控除後の発注額。前払を切捨て、残金に端数を載せる。複数明細の最終納品予定日を納品基準とし、未定日があれば残金日も未確定。分納時の起算日と請求配分は要確認。
- 対応する自動条件は50/50、30/70、納品月翌月末100％。営業日、休日補正、締日例外、入金後などは手入力。自動計算できるような表示はしない。
- 在庫の使用予定は確保しない。引当が確定したら別操作で登録。引当の責任者・期限、使用不可の判定・復旧・廃棄、在庫棚卸調整、返品は今後の確認対象。
- 移管は担当者1段階の確認。案件間は引当残を移し、倉庫間は未引当品または同一案件の引当品を移す。申請では在庫を予約しない。申請時・完了時に数量を検証。承認者・段階、移送中在庫の扱いは要確認。
- 未納取消だけを処理する。納品済実績を削除せず、前払精算・返金・支払予定の見直しは自動処理しない。差額で確認する。
- 請求書欄の日付の意味を要確認。新規の請求日・受領日・確認日は別項目。購買の確認済は経理の支払確定を意味しない。
- 仕入先・期間で在庫を絞ると該当発注が含む製品の事業内在庫全体を表示する。仕入先別ロット管理は未実装で、画面に明示。
