## 共通実装

`noticeCenter` に通知データ、閲覧判定、フィルター、既読、描画、一覧・詳細モーダル、トースト、イベント生成を集約した。部門固有の通知UIは複製しない。既存の3種類の描画処理に共通カードを差し込むアダプターを追加した。

- 見出し、画面の閲覧範囲全体の未読数、すべて見る。
- すべて／全社共有／プロジェクト進捗／承認、未読・要対応のAND条件。
- 通常は最大5件、一覧は同じカテゴリー・補助フィルターで全件表示。
- 緊急→未対応の依頼→その他、同順位では発生日時降順。日時は日本時間で表示する。
- 指定色のカテゴリー・グレーの詳細種別、事業の補助表示、状態・優先度、案件番号・名前、発信部門、日時、期限を表示。既読になってもカテゴリー色は変更しない。
- 既読は利用者ごと・通知ごとに共有。カテゴリーや補助フィルターを変えても、未読バッジの集計範囲は変えない。
- 詳細を開くと既読になるが、関連業務を完了しない。通知詳細には承認・完了ボタンを設けない。
- 状態・要対応判定は保存済みの関連業務を参照。契約の再申請では通知対象の版も更新し、過去の依頼を再び要承認にしない。
- 「期限間近」は既存の業務デモ基準日2026-11-04から3日以内の未対応期限というモックのルール。
- 関連画面への遷移は事業・案件・部門を明示し、電力申請は既存 `powerSectionFor` で工程を選ぶ。契約承認は該当案件・契約区分の既存入力欄を開く。未実装・未登録の遷移先は本文と未実装メッセージを表示し、代替案件を開かない。
- 白背景、薄い区切り線、レスポンシブな行・タグ・モーダル。CSSは `.nc-*` に限定する。

## データ・内部ID・閲覧範囲

通知にはID、イベントID、カテゴリー、詳細種別、件名・本文、事業、案件内部ID・表示番号、発信部門、対象部門・利用者・ロール、発生日時、期限、優先度、遷移先、利用者別既読、関連業務の参照を保持する。

既存デモ案件は表示番号が `id` であり、番号と独立した不変の案件内部IDは未実装だった。このため元の案件オブジェクトにWeakMapで画面内の内部IDを割り当て、そのオブジェクト参照へ通知を紐付けた。表示番号や住所を通知の永続キーにせず、既存番号体系や業務データは変更していない。同じ表示番号を持つ蓄電池・太陽光は別の参照になる。サーバー内部IDへの接続は未実装であり、再読み込みするとこのレジストリーも初期化される。

既存設定画面の利用者・権限テンプレートは認証・権限の実装ではない。通知の「通知デモの閲覧者・保存範囲」から、以下のサンプルプロフィールを切り替えられる。

| プロフィール | 通知の閲覧対象 |
| --- | --- |
| 兼務担当（初期） | 全7部門、担当者・関係者、既存案件すべて |
| 一般担当 | 電力申請のみ、P-00002・G-00004・G-00005の蓄電池案件 |
| 部門責任者・承認担当 | 営業・法務、責任者・承認者、設定された一部案件 |
| 閲覧対象なし | 0件・空状態を確認するためのプロフィール |

部門所属、通知先部門、通知先利用者またはロール、事業、案件閲覧範囲を共通処理で判定する。対象外通知は表示内容・件数・トーストへ渡さない。既存の画面全体にはアクセス制限を追加しない。これはフロント側のデモ制御であり、本番の権限制御ではない。

サンプルは全社案内、既存の部門保存状態、既存契約の承認済み・承認待ちを参照する。初期状態を共有するサンプルであり、未実施の工程完了や正式化承認を捏造しない。データセンターに通知用の案件は追加していない。

## 接続した操作

既存の保存処理を呼ぶ前後で、通知対象の保存済み値だけを比較する。検証失敗、取消、入力途中、再描画、タブ切替、同値の保存、メモ・住所等の軽微な更新では通知を作らない。

| 既存操作 | 通知対象 |
| --- | --- |
| `departmentSave` | 部門の状態、契約確認・締結状態、主要実績・予定・対応期限の実変更 |
| 同処理の契約 `*Approval` | 承認待ちへの変更を承認依頼、承認済みを結果、差戻しを差し戻しとして通知。契約IDで重複を排除する |
| `salesSave` | 既存太陽光営業のステータス、契約日、完工・検収・引渡し予定の実変更 |
| `powerSave` | 接続検討・本申込・回答・アグリ本申込・連系協議・受電／供給開始・市場参入等の主要日付、見込・予定、対応状態の実変更 |
| 工事の引渡実績の保存 | 工程完了を反映し、メンテナンスにも引き継ぎ通知を表示 |
| 再接続検討の確認実行 | 申請回の変更として1件だけ通知。退避・初期化される各項目から大量通知を作らない |
| 太陽光の既存「請求指示」確認 | 画面内の請求指示状態が初めて変わったときに通知。同じ依頼の再実行は通知しない |

イベントIDで重複を防止する。1回の保存で承認変更が含まれた案件は、その案件の進捗通知を抑止し承認通知を優先する。共有契約・共有工程は意味上の同一項目を1回だけ比較する。

通知先の関係部門・ロールはデモ用設定。主要実績の関係部門への共有は通知の宛先設定であり、新しい承認・業務フローの実行ではない。

## 保存・プッシュの範囲と未接続項目

- 通知・既読・フィルターはメモリー内のみ。再読み込みで初期サンプルに戻る。localStorage・サーバー保存へ変更していない。
- 新規イベントだけを対象に、現在のデモ利用者の閲覧範囲と通知種別を判定して最大3件の画面内トーストを表示する。初期ロード・部門や事業の切替では表示しない。
- OS／ブラウザへの実プッシュ、通知許可要求、メール、Slack、外部サーバー送信は実装しない。
- 正式な利用者・担当・責任者・案件ACL・承認者マスターとの接続は未実装。設定画面での変更を認証・通知対象の実設定と扱わない。
- 段階承認の進行・現段階の承認者割当、承認申請専用操作、正式化承認の実行、却下の業務操作は既存モックにないため新設していない。共通通知データ・`emit` はこれらの通知種別を受け取れるが、実操作には未接続。契約の承認状態入力と、正式な承認フローを区別する。
- 添付本体・会計・ANDPAD・監視・バックエンド等の外部イベントは未接続。軽微な編集や任意の全項目変更を一律通知する実装ではない。
