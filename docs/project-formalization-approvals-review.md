## 操作方法

ヘッダー右上のユーザーメニュー内「操作ユーザー（デモ）」で「管理者（承認管理デモ）」または既存の「部門責任者（営業・法務／承認担当）」に切り替える。「設定」の上に、部門メニューと区切って「承認管理」と承認待ちバッジが表示される。一般担当・兼務担当・閲覧対象なしには表示しない。

既存の通知閲覧者デモの利用者・所属・ロール・案件閲覧範囲を共用し、管理者プロフィールを追加した。設定画面の権限テンプレートを認証システムとして扱っていない。承認者は既存の案件閲覧範囲に限定され、管理者は全案件を確認できる。画面表示だけでなく確認・承認・差戻しの各操作でも判定する。

## 自動申請の条件

| 条件 | 既存の保存先と判定 |
| --- | --- |
| 電力申請確定 | 共通案件の `powerConfirmedAt` に有効な日付がある |
| 不動産取得完了 | 同じ案件の不動産情報 `status` が「取得済み」または「取得済」、かつ `acquiredDate` に有効な日付がある |

蓄電池では既存の `case.departments.realestate` を使用。電力申請の既存確認記録は、基本情報・設備仕様の「電力申請確定日（正式化の完了条件）」から既存の下書き・保存・取消で更新できる。保存用フィールドは同じ共通日付へのアクセサーで、独立した確認記録を二重保存しない。本回答文書発行日・申請日・連系日からの推測は行わない。

太陽光は既存の共通案件と不動産レコードを参照する。既存の太陽光電力申請画面は準備中であり、確定記録がなければ条件不足とする。データセンターは既存案件がなく、架空案件を追加しない。エンジンは3事業を扱うが、未実装の事業別入力フローは新設しない。

初期保存済みデータを1回評価し、その後は実際に保存値が変わった場合だけ再評価する。入力途中・取消・入力エラー・同じ値の再保存・画面再描画では申請を作らない。「完了報告」「承認申請」ボタンは追加しない。

対象は内部の初期表示番号がG-/R-である仮案件。P番号発行済みの案件は申請・再採番しない。承認レコードは既存通知レジストリの安定した内部IDで一意に保持し、重複申請を防ぐ。既存デモのG-00010は両条件が成立しているため、初期表示で1件の承認待ちとなる。既存P案件は6レコード（事業別の既存デモ）を承認済みの参照として表示し、未記録の承認者・日時を捏造しない。

## 状態遷移

- 未申請 → 両条件成立の保存 → 承認待ち。
- 承認待ち → 承認直前にも両条件・権限・状態を確認 → 承認済み＋正式番号発行。
- 承認待ち → 理由と差戻し先部門を指定 → 差戻し。理由・実行者ID／氏名・日時・部門を履歴に記録。
- 差戻しのまま条件が残っていても再申請しない。差戻し先部門による実際の変更保存を記録し、両条件が成立した時点で再申請する。他部門だけの変更、同じ値での保存、下書きは修正保存と扱わない。
- 承認待ちの途中で条件が不足 → 未申請として承認対象から除外。履歴は保持し、承認待ちタブの「条件不足で承認対象外」に表示。理由を確認でき、承認ボタンは無効。条件が再び成立した保存で自動申請。

承認済みの正式案件は、後から条件値が変わっても再採番しない。現在の条件不足は案件詳細に表示する。

## 番号とデータの保持

内部ID・既存オブジェクト・各部門のデータキーは変更しない。`formalNumber` にP-00001形式の5桁表示番号を記録し、`previousNumbers` と承認履歴に旧G/R番号を残す。

既存の事業別デモには同じP番号があるが、これらは変更せず予約番号として扱う。全事業の既存P番号・発行済み番号を避け、最大値の次を画面内で発行する。発行時にも予約番号を再確認し、5桁上限ではエラーにする。同期処理中フラグと承認状態の再確認で、二重クリックによる重複承認・重複採番を防ぐ。

7部門の一覧・データ入力・案件詳細・案件選択、全社トップ・通知の表示番号は正式番号を参照する。旧番号・新番号の両方で検索可能。契約ID、部門別レコード、添付名、タスク、通知の内部参照はそのまま保持する。

## 確認画面

承認待ち・差戻し・承認済みタブ、案件番号／名称検索、登録日時・仮番号・案件名・事業・担当者・両条件・承認状況・確認ボタンを実装。確認画面は基本情報、保存済みの両条件、登録済み資料名・契約情報、承認履歴と明示的な承認／差戻しを表示する。根拠資料名はサーバーで閲覧できるようには見せない。

各案件詳細の上部にも承認状況・両条件・条件不足・直近の差戻し理由・履歴・正式番号を表示する。案件が検索結果に存在しない場合は、別案件の承認情報を表示しない。
